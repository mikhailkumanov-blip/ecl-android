# VV Курьер PRO

Android MVP для одного автокурьера: проверенный список назначенных заказов → дорожная матрица → последовательность доставок с индивидуальными окнами. Kotlin, Jetpack Compose, Room, Coroutines; Android 8.0+ (API 26), целевая версия API 35. Приложение независимо от ВкусВилла и не управляет официальным приложением.

**Статус сборки:** исходный проект подготовлен; успешная сборка подтверждается только зелёным завершением workflow [Android APK](https://github.com/mikhailkumanov-blip/ecl-android/actions/workflows/android.yml). Наличие этой инструкции само по себе не подтверждает готовность APK. Проверка на физическом POCO F7 ещё не выполнена.

[Установка на телефон без компьютера](docs/INSTALL_RU.md) · [Дорожная матрица и GraphHopper](docs/MATRIX.md) · [Данные и приватность](docs/PRIVACY.md)

## Что делает MVP

- Импорт нескольких изображений через Android Photo Picker и системное меню «Поделиться»; локальный Tesseract с моделями `rus+eng`.
- Извлечение номеров заказов, адресов, окон, таймеров, вознаграждения и веса; объединение по ID с предупреждениями о несовпадениях. Совпадающий адрес сам по себе не означает дубликат.
- Обязательная проверка карточек и подтверждение принадлежности к «Мои». «Доступные» не считаются назначенными заказами. OCR может ошибаться; активную вкладку нельзя надёжно определить по одному тексту.
- Сравнение исходной последовательности и рассчитанного маршрута, прибытия, завершения обслуживания и запаса до срока. Исходная последовательность — порядок принятых карточек; сверяйте его с официальным приложением.
- Учет обслуживания, ожидания начала окна, возврата в даркстор, закреплённых позиций и запрета менять порядок компании.
- Пересчёт после отметки доставки, открытие адреса в Яндекс Навигаторе, голосовое предупреждение при малом запасе после пересчёта.
- Доход по выполненным заказам, заказы в час, введённый фактический пробег, оценка топлива и дохода после топлива. Налоги, ремонт и амортизация в оценку не включены; гарантии роста дохода нет.

## Первый запуск

1. Откройте «Настройки» → «Загрузить демо · 10 заказов». Это полностью условные данные и **синтетическая матрица**, без сведений о реальных дорогах или пробках Москвы.
2. На вкладке «Маршрут» сравните последовательности, сроки и запас. Пункт «Доставлено · пересчитать» исключает выполненный заказ и принимает его адрес за текущую точку.
3. Удалите демо перед реальной сменой. Во вкладке «Импорт» укажите **московскую дату и время получения информации со скриншота**, затем выберите изображения. Для старых скриншотов не используйте текущее время.
4. Проверьте ID, адрес без квартиры/кода, абсолютные начало и дедлайн, оплату, вес и обслуживание. Подтвердите каждый заказ из «Мои». Для обратного отсчёта дедлайн вычисляется относительно указанного времени получения информации; старые данные требуют повторной сверки.
5. Импортируйте дорожную матрицу JSON либо введите координаты всех точек и даркстора, свой API-ключ и явно запустите GraphHopper Matrix. Запрос может расходовать квоту/средства вашего тарифа. Ключ не сохраняется между сеансами.
6. Проверьте ограничения компании, возврат, раннюю передачу и закрепления. Запустите расчёт. Без матрицы реальные километры и точное прибытие не вычисляются.

Парковка, подъезд, лифт и передача задаются суммарным полем «Обслуживание · минут» для каждого заказа. Дедлайн относится к **завершению обслуживания**, а не только к приезду автомобиля. Если ранняя передача не разрешена, курьер ждёт начала окна и только затем обслуживает заказ.

После завершения доставки началом следующего расчёта считается точка выполненного заказа и текущее время телефона. Если вы уже уехали в другое место, этот прогноз требует актуализации исходной точки; MVP не отслеживает GPS и не оценивает движение в фоне. При изменении дорожных условий обновите матрицу и пересчитайте маршрут.

## Алгоритм и честные ограничения

`core` не зависит от Android. Оптимизатор использует полную направленную матрицу автомобильного времени в секундах и расстояний в метрах. Пара точек A→B может отличаться от B→A; расстояния по прямой в рабочий расчёт не подставляются.

Критерий лексикографический:

1. Число опоздавших заказов.
2. Суммарное опоздание, затем максимальное опоздание.
3. Общий пробег, включая возврат, если он включён.
4. Время финиша, включая ожидание и обслуживание.

Любой маршрут без опозданий лучше любого маршрута с опозданиями. Среди допустимых маршрутов решает пробег, затем время. При невозможных сроках показываются величины нарушения.

До **10 активных заказов** выполняется точный поиск с безопасным отсечением ветвей. Для **11–20** используется ограниченный beam search и улучшение перестановками: глобальный минимум и невозможность уложиться в сроки не доказываются. Если эвристика показала опоздания, это не доказательство отсутствия другого допустимого порядка. В интерфейсе это отмечено.

Дорожная матрица — снимок условий, а не гарантия прибытия. Матрица старше 15 минут отмечается как устаревшая. Базовый GraphHopper Matrix в этой интеграции не предоставляет живые пробки. Прогноз может отличаться из-за движения, парковки и фактического обслуживания. Закреплённые позиции не могут противоречить друг другу и правилам компании.

## Проверка и сборка

GitHub Actions использует JDK 17, Android SDK 35 и Gradle 8.11.1, загружает официальные OCR-модели Tesseract `tessdata_fast` версии 4.1.0 (commit `65727574dfcd264acbb0c3e07860e4e9e9b22185`, проверка Git blob-хеша), затем выполняет:

```sh
gradle --no-daemon :core:test :app:assembleDebug :app:lintDebug
```

При успешных проверках APK публикуется как artifact `VV-Courier-PRO-debug`; отчёты тестов и lint — как `checks`. В репозитории нет Gradle wrapper JAR: workflow устанавливает фиксированную версию Gradle через `gradle/actions/setup-gradle`. Для локальной сборки нужны Gradle 8.11.1, JDK 17, Android SDK 35 и настроенный `ANDROID_HOME`; выполните `bash scripts/build.sh`.

Тесты проверяют сценарий 10 заказов, разные окна, ожидание, завершение обслуживания, перестановку, два заказа на один адрес, недостижимые сроки, закрепления, асимметрию матрицы, возврат, пересчёт от выполненного заказа и сохранность всех 20 заказов. Отдельные тесты покрывают OCR-парсер, конфликты ID, вкладки и обратные таймеры. Это не заменяет проверку распознавания на ваших скриншотах и испытание на телефоне.

## Структура

- `core/` — модели, TSP с временными окнами, OCR-парсер и JVM-тесты.
- `app/` — Compose, MVVM, Room, локальный OCR, импорт, дорожный адаптер и навигация.
- `.github/workflows/android.yml` — тесты, lint, сборка и APK artifact.
- `scripts/prepare-ocr.sh` — загрузка моделей **при сборке**; на устройстве OCR работает локально.

В публичном репозитории допустимы только код и обезличенные тестовые данные. Не добавляйте скриншоты реальных заказов, выгрузки базы, API-ключи и персональные данные клиентов.
